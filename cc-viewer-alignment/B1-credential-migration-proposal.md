## 需要确定的兼容行为

本地旧版只会从 preferences 中读取 Base64 密码、从 profile 中读取 apiKey、从 `im/dingtalk/config.json` 读取 appSecret。上游加密迁移会把凭据写入 AES-256-GCM vault，读回确认后从旧字段移出。

旧二进制不理解 vault；尤其迁移前的认证读取器会把缺失密码当作空密码，可能进入原来的无密码放行分支。`dc883f3` 已防止新版这样处理，但无法修补仍在运行的旧二进制。因此不能在用户未选择共存策略前自动剥离字段。

| --- | --- |
| 升级后仅新版运行（推荐） | 迁移前关闭共用配置的旧进程，备份并逐项迁移到 vault；以后同配置只用新版。回退旧代码前，先用备份恢复旧配置；不直接把旧版指向已迁移配置。 |
| 旧版必须继续共用配置 | 不能直接清除旧字段；需另行设计隔离配置/兼容期。旧格式仍含可逆或明文凭据，不能把这种状态描述为已完成静态凭据加密。 |

## 单版本方案的逐笔实施顺序

1. 独立提交 vault 密码学原语，仅用 Node crypto：AES-256-GCM、每条随机 IV、版本化格式、kind/ref 绑定，认证标签或编码损坏必须报不可读；先不接入启动或用户配置。
2. 独立提交私有 key/store：复用现有原子替换和锁，严格读取，私有目录/文件权限；ciphertext 已存在但 key 缺失时禁止创建替代 key。凭据根在启动时冻结，运行中改变 logDir 仍要求重启。
3. 在接入真实凭据前完成 vault/key/备份的文件读取边界保护，覆盖 realpath、符号链接、HTTP 文件端点、归档及 IM 附件；不能依赖隐藏文件名。B0 已复现的项目相对符号链接越界仍需处理。
4. 按 auth、proxy profiles、DingTalk IM 分别小提交接入；运行时先读 vault，所有不可读路径拒绝，不自动变成空值或转发默认凭据。保留 API 遮罩、稳定 profile 身份及明确空密码模式。Codex 原生 auth.json 不参与。
5. 独立提交迁移工具：先产生可恢复的私有备份，持有源配置锁，写密文、读回比对，再剥离该字段；失败不改原字段。幂等以数据和版本判断，不能只看完成标记。确定旧进程已停用后才启用迁移。
6. 独立验收正常升级、失败恢复、丢 key、坏 ciphertext、并发、旧字段再次出现、重启及回退。回退需同时恢复匹配的配置、vault/key 和迁移状态，不能仅 revert 代码后启动旧读取器。

## 运行时保存的原子性细化

现有 source JSON 与 vault 是两个独立文件，不能直接“覆盖当前密文，再保存 source”：source 的原子 rename 失败时，用户会收到失败但有效密码已改变。复用现有 store 的 kind/ref 与原子 source 写入，采用不可变的随机版本引用：先为该配置/作用域暂存新密文并读回，再原子切换 source 的引用；配置写失败时旧引用/旧密码仍有效，不依赖一定能成功的回滚写。提交后清理旧引用；清理失败不推翻已成功的配置保存，遗留密文由私有策略保护并记录为待清理，不在 API 中暴露。读取引用须验证归属，禁止跨配置或作用域引用；明确空值仍存为有值的加密记录，缺失记录为不可读。

该机制只是实现细化，不自动迁移旧格式。auth/profile/IM 分别以明确版本标记启用对应读取器；只有迁移工具在旧进程已停用、备份及全部暂存验证通过后，才原子切换各自 source 格式。未迁移的配置继续原格式，迁移后的配置拒绝旧字段重新出现。不会仅因私有目录或测试记录存在而启用迁移。


代理已有自动备份 `${PROFILE_PATH}.bak`，不能在保存新引用后立即删除备份仍使用的旧密文。保持现有“当前配置 + 最近一次备份”的恢复语义：保存后保留这两份 source 引用的版本，下一次备份替换成功后才清理不再被二者引用的旧版本；保存失败保留有效 source。迁移工具需同时处理当前 profile 与已知 .bak，并在私有备份中保存它们匹配的 vault/key，不能仅替换明文字段后留下一份无法解密的 .bak。
